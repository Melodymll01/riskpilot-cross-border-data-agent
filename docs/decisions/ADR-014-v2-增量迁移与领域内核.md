# ADR-014：V2 采用增量迁移并保留领域内核

- 状态：已接受
- 日期：2026-08-06

## 背景

当前系统已经具有 FastAPI、Pydantic、DDD 分层、Port、SQLite、ChromaDB、审计、
用户隔离、文档解析和大量离线测试。直接使用新的 Agent 框架重写全仓，会同时改变
业务模型、存储、检索和编排，难以验证收益，也会让现有能力长期不可用。

## 决策

1. 保留 `domain → app → infra/api` 的依赖边界。
2. 新能力使用 `/api/v3` 和新的 Workspace/Case 领域对象增量建设。
3. `/api/v2` 在 V3 达到替代门槛前保持可用。
4. 新旧模型不共享同一张业务表，不在迁移初期修改 v2 Task 语义。
5. 每个迁移步骤必须有独立测试和独立 commit。
6. V3 领域模型不得依赖 LangGraph、FastAPI 或具体存储组件。

## 备选方案

### 全仓重写

拒绝。改动面过大，无法区分业务重构收益和框架迁移收益。

### 直接扩展 v2 Task

拒绝。Task 同时承担聊天会话和业务案件会使状态、权限和生命周期继续混杂。

## 结果

- 可以并行运行 v2 和 v3。
- 新设计可以通过小步提交持续验证。
- 迁移期会暂时存在两套 API 和数据模型，需要明确退役门槛。
- 完整替代后再单独删除 v2，避免在功能建设提交中混入大规模清理。
